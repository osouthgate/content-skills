# Evidence and limits

Supported inputs: Codex rollout JSONL tool-call/output and turn-aborted events; Claude JSONL assistant tool-use/user tool-result records; explicit hook error events; read-only Codex `logs` SQLite records. Coverage counts valid records with no recognised finding as `unclassified_records`, including unsupported formats and ordinary chat/telemetry. Malformed and oversized records have separate warnings. No raw content is persisted. Tool names and error excerpts are deliberately omitted, so arbitrary logged text cannot leak through an imperfect redaction pattern.

`hook_error` requires a structured hook error event or an ERROR/WARN harness log whose target names hooks and whose body reports failure/error/non-zero exit. `hook_error_reported` is weaker: a tool output contains a hook-style error line. Inspect local evidence before treating it as a reproduced hook fault. `tool_failure` requires a structured error flag. `tool_failure_reported` is weaker textual non-zero exit evidence; quoted reports and source reads can repeat old failures. Other text-derived stop categories also count observations, not distinct incidents. `tool_call` counts outer observed calls; nested calls within `functions.exec` are not reconstructed. It does not prove success. No claim of complete call/output pairing is made across truncated windows.

Special classifications are `policy_refusal`, `review_limit`, `billing_block`, and `intentional_interruption`. They explain stopped work without inferring broken hooks. A user report of recurring failures remains unverified until an affected hook/event is captured. Categories can coexist, such as a non-zero tool exit caused by a policy refusal.

Source identifiers hash the local absolute filename; record positions are byte offsets or SQLite row ids. Use those locally to locate evidence; the report never includes the filename. Daily checkpoints also retain only hashed ids, inode/device, offsets and numeric counters. SQLite query reads at most the most recent 2,000 rows (optionally filtered by thread) and truncates each body to 16 KiB. JSONL defaults: 64 files, 8 MiB per file, 32 MiB overall, 256 KiB per record. Initial large files start at a tail boundary and explicitly report skipped history. Incomplete final records are retried next run. Rotation/truncation resets that source cursor and reports replay risk. Bounds may miss faults; warnings are actionable coverage gaps, not proof of corruption.

Recent Codex discovery uses file modification time, not the creation date encoded in its containing folders. It traverses only the fixed year/month/day tree, skips symlinks, examines at most 4,096 directory entries and reports discovery counts/caps. Recent date folders are visited first; all matching files found within the budget are ordered by modification time before the 64-file scan cap. An old active session can still be outside a capped discovery window: include it explicitly when important. No claim of discovering every active session is made after a cap or unavailable directory.

# Daily use and recovery

Daily mode only writes inside a monitor-owned private state directory. It uses a non-blocking lock; overlapping runs refuse rather than race. A corrupt checkpoint stops incremental scanning instead of silently discarding history. Explicit `repair --action reset-checkpoint --apply --expect HASH_FROM_PLAN` backs up only the monitor checkpoint; `tighten-permissions --apply --expect HASH_FROM_PLAN` sets the monitor directory to 700 and its own fixed files to 600. The hash guards against stale plans. Repairs reject symlinks and non-owned directories/files. There is no command runner, hook editor or arbitrary repair recipe in the plan.

Scheduling and actual hook changes are separate owner decisions. Daily mode is suitable for an existing scheduler once authorised; it never enables one itself. Review findings, fix a demonstrated cause in versioned source, run meaningful fixture tests and the previously failing action, then check whether the next audit shows recurrence. Do not call the system healed merely because the monitor repaired its own cache.

Extend healing only after a fault is confirmed: add a named repair adapter with a specific evidence signature, exact affected file/component allowlist, precondition hash, bounded action, rollback artifact and reproducible success/failure test. Have it emit a plan first and require explicit apply for that repair. A log entry must never select an arbitrary command or path. Before calling a hook repair successful, rerun the original triggering action with the checks still enabled and observe the hook completing normally. Until such an adapter is reviewed and authorised, daily runs diagnose and deduplicate; they do not repair hooks.
